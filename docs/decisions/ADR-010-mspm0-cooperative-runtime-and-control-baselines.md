# ADR-010：MSPM0先采用确定性协作式运行时并冻结已验证控制基线

- 状态：Accepted
- 日期：2026-07-31
- 部分修订：ADR-009（Q2 的任务所有权）

## 背景

MSPM0 当前的 `main.c` 同时承载初始化、菜单、Q2/Q4/Q5/Q6、循迹、轮速 PI、
LCD、日志和中断处理。问题的根因不是“没有 RTOS”，而是同一硬件和状态存在多个写入者，
且周期任务混用阻塞延时、循环次数和中断回调。此时直接加入 RTOS 只会把已有的所有权冲突
变成跨线程竞态，并增加栈、优先级和队列调试成本。

同时，Q2、Q3 和 Q4 已分别存在实机验证过的版本。架构迁移必须先保护这些基线，不能把
“重构后能够编译”等同于控制效果未改变。

## 决策

### 1. MSPM0 暂不引入 RTOS

先使用由 1 ms SysTick 驱动的确定性协作式运行时。中断只发布有界事件或计数；前台任务每次
执行必须有界、不得等待外设或按键：

| 任务 | 周期/触发 | 责任 |
|---|---:|---|
| SafetySupervisor | 1 ms | 新鲜度、故障锁存、请求执行器禁止 |
| CAN Transport | 1 ms，Q3～Q6 | 有界收发预算，只搬运帧 |
| IMU Parser | DMA/UART 事件，源 200 Hz | 解析已交接的数据块并发布快照 |
| Mission/Chassis Runtime | 5 ms | 任务生命周期和底盘动作执行 |
| Button Input | 5 ms | 低有效采样，20 ms 非阻塞消抖，发布事件 |
| LineFollower | 10 ms | 灰度快照到运动意图/事件 |
| WheelControl | 100 ms | 左右轮独立 PI |
| LCD | 不高于 10 Hz，dirty-only | 人机状态，不参与控制时序 |
| LED/Buzzer | 事件驱动 | 非阻塞提示 |
| Logging | 低优先级、有界 | 丢弃优于阻塞控制 |

SysTick、编码器、WIT DMA/UART 和 CAN ISR 均不得运行 PID、循迹决策、浮点解码、LCD 或
蜂鸣器逻辑。到期标志使用饱和计数而不是单个布尔量，以便检测 deadline miss 而不发生无界
补跑。

只有在测量证明出现以下任一情况后，才重新评估 MSPM0 RTOS：持续 CPU 利用率超过 70%、
任务存在超过 1 ms 的不可消除阻塞、持续 deadline miss/队列溢出，或多个独立高频工作负载
无法被有界调度。若届时引入 RTOS，只允许静态任务、静态队列和静态内存，不使用运行期动态
分配。

### 2. 固定硬件与状态所有权

- `Motor HAL` 是方向 GPIO、PWM 和 STBY 的唯一寄存器写入口。
- `ChassisActuator` 是正常运行时唯一的 Motor HAL 调用者。
- `SafetySupervisor` 只能提交 inhibit 请求，不能直接写电机寄存器。
- `LineFollower` 只消费带 `valid + timestamp` 的灰度快照并返回 `MotionIntent`/事件。
- `WheelControl` 独占左右轮 PI 实例和编码器快照。
- `Mission Runtime` 独占正常任务的启动、停止、阶段、圈数和完成状态。
- `SafetySupervisor` 独占故障锁存和强制禁止；子模块不得修改全局 `start`。
- `CAN Transport` 只收发帧；协议适配层不能决定任务阶段。

### 3. 按题目路由任务所有权

- Q2 为 MSPM0 本地任务：SW1 接受执行后无需等待 M33 `RUNNING`，比赛业务 CAN 与 WIT
  处理保持静默，避免破坏已经验证的循迹时序。
- Q3 为 EdgeTalk 滚球任务：MSPM0 底盘保持 STBY 低，不参与滚球控制。
- Q4～Q6 由 EdgeTalk M33 持有全局任务状态，MSPM0 只执行通用底盘意图并上报事件。

因此，本 ADR 对 ADR-009 中“Q2～Q6 全部由 M33 持有任务状态”的表述增加 Q2 本地例外；
Q3～Q6 的集中编排原则不变。

### 4. 冻结已验证控制基线

| 项目 | 可信来源 | 迁移期间不可无意改变的内容 |
|---|---|---|
| Q2 | `db1bdee`；稳定 ZIP SHA256 `596A847BCE550BE9466EE30CB2A494CEABCFA6BA5D18C15279DB86101BD47A8D` | 约 10 ms 循迹节拍、100 ms 轮速 PI、参数、方向符号、起步和终点检测 |
| Q3 | `56a4caa` | PID `0.70/0.15/0.40`、静态 boost 0、IMU 前馈关闭、水平位 `1.7205 rad`、限幅 ±3°、+50/−50 mm 的 150/300 ms 稳定判据、通过后保持 −50 mm |
| Q4 | `5c168c3` | 已验证的电机方向和直接起步行为；不得恢复未经验证的 28→50、800 ms 起步斜坡 |

架构提交不得顺带调参。任何基线变化必须是单独提交，先有能复现实物问题的测试/日志，后有
明确的台架验证记录。

## 迁移顺序

1. 用测试固化任务路由、Q2/Q4 参数和启动行为。
2. 建立纯任务策略：Q2 本地、Q3 禁止底盘、Q4～Q6 分布式。
3. 修复启动顺序，使 LCD/背光先于可能阻塞的菜单或运行时入口。
4. 按任务启停 CAN/WIT 业务处理，不改 Q2 循迹块。
5. 建立快照、到期计数和协作式调度器，再逐步把 ISR 工作移到前台。
6. 收拢 Motor HAL 唯一写入口，最后提取 LineFollower、WheelControl 和 Mission Runtime。

每一步必须保持 host 测试和固件构建通过，并形成独立可回滚提交。自动化验证不得使能电机或
触发自主运动。

## 2026-07-31 目标板验证补充

Keil `-O0` 反汇编确认 `lap_test_once()` 分配 `0x30C`（780 B）局部栈帧，另有 20 B
寄存器压栈；TI MSPM0G3507 SDK 2.05.01.00 默认启动文件却只保留 `0x100`（256 B）栈。
Horco CMSIS-DAP（UID `2d2670f3`）断点复现到：进入函数前 `tick_total == tick_ms ==
0xFF`，执行函数序言后 `tick_ms` 被栈写入清零。这是确定的内存破坏，不是状态机时序或
PID 参数问题。

项目因此在不修改已安装 TI SDK 的前提下，先链接 `0x700` B 的 `STACK` 扩展段，再链接
官方 `0x100` B 启动栈，形成连续 `0x800`（2 KiB）有效栈。命令行和 uVision 都显式保留
扩展符号；命令行构建还会检查所有 STACK 段连续且 `__initial_sp` 位于最高端，条件不满足
就拒绝生成 HEX。

实机烧入 HEX SHA-256
`C8F47D24F8DAAB42EA212ADFBC6ABE30F5D5E8F464E0BC92A20E2DE1404A1F93` 后，只复位到
菜单态，未模拟按键、未使能任务运动。进入 `lap_test_once()` 和到达 `motor_init()` 时两份
tick 均保持 `0x103`；后者 SP 为 `0x20201C48`，距栈底 `0x202017B8` 仍有 1168 B。
稳定 1 s 调试窗口记录 1016 个 tick、1015 次 CAN 前台服务、pending 为 0；调试器
halt/resume 只增加 1 次 deadline miss。主机测试 45 项通过，Keil 构建明确输出
`Verified target stack: 0x800 bytes`。

同一目标板随后验证了 WIT ISR 前台迁移。固件 HEX SHA-256 为
`B9860713093421EF035BF9B018273DF29D28AFB446C72023ABDE77349B651F92`；DMA/UART ISR
只把字节写入 256 B 单生产者/单消费者队列，1 ms 前台服务每次最多解析 32 B，并在同一
release 内先于 CAN 快照执行。稳定 1 s 差分为：加速度帧 `+201`、角速度帧 `+201`、
姿态角帧 `+200`、有效帧合计 `+602`；入队和前台处理均为 `+6636 B`，队列深度为 0、
drop 增量为 0，符合 JY901S 三类报文各约 200 Hz 的配置。

启动 LCD 和首屏绘制期间前台尚未开始 poll，队列会达到 256 B 并丢弃旧的启动数据；本次
观测累计丢弃 6504 B，但进入菜单后约 8 ms 可排空，稳定窗口不再丢弃。这不影响按键启动前
的最新 IMU 数据，但它仍是明确记录的启动期现象；后续若要求上电即连续记录，应把初始化
阶段改成 service-aware，而不是扩大队列并延长旧数据滞留。

Motor HAL 硬件写入收拢后，提交 `ea497f0` 通过 50 项主机测试和 Keil 构建，构建仍明确
验证 `0x800` B 栈。本次烧入 HEX SHA-256 为
`AE1A07FEE8AD643291339549C97F7CD7A35AF2E9BAA3EF191C65E44BBE640FFE`；pyOCD 在复位下
擦除并编程 48128 B，随后显式 reset/go。菜单态 GPIOA `DOUT31_0` 为 0，PA13/STBY
的输出使能位为 1、引脚读回为 0，证明电机驱动保持禁止。稳定约 1.1 s 窗口内，加速度、
角速度和姿态帧各增加 221（约 201 Hz），有效帧增加 663；启动期后 drop 保持不变，
队列由 1 B 排空到 0。CAN/IMU 前台服务各增加 1114，pending 为 0；本次新增的 2 次
deadline miss 与两次调试器 halt 一一对应。

同一台架空底盘在 EdgeTalk 和 RS00 接入时做了只读 CAN 观测，未发布按键事件或运动指令。
MSP 能收到扩展帧以及 `0x082` 标准帧，说明 RX 和位时序并非完全断开；但 MSP 的首个
mission intent 没有 TX confirmation，TEC 升到 248 并进入 bus-off，延时恢复后再次 bus-off。
因此这次实机不能认定 Q3 端到端通过；故障位于 MSP TX/ACK 物理或接口层，优先检查
TXD、收发器 EN/STB、共地和终端，不通过修改 mission 协议规避。Q3 状态机、已冻结 PID
参数和 M33/M55 shadow 路由的 14 项定向主机测试仍全部通过。

提交 `49dfa95` 随后删除了从未启用的 TIMER0 ISR PID/电机接管分支；ISR 仅发布左右
编码器增量，不再读 IMU、运行 PID 或写电机。新回归测试按红-绿流程先证明旧分支存在，
再使定向测试通过；全部 52 项主机测试和 Keil 构建通过。烧入 HEX SHA-256 为
`6D17E86E93BBAB30BA1D7A2F61B660C46CE2BFDE8893EEE59AF0AA3EA09A7E4A`，pyOCD 擦除并编程
53248 B。复位后运行约 3.2 s，编码器原始计数和已发布增量均为 0，STBY 的输出值和引脚读回
仍为低；加速度/角速度/姿态帧分别为 441/441/439，队列已排空。同期 CAN 仍在收帧
的同时因 MSP TX 无确认反复 bus-off，证明该现象与 ISR 控制分支删除无关。本次未自动启动 Q2，
实际循迹效果仍需操作者手动按键验收。

## 后果

- 先消除共享状态和硬件写入冲突，再决定是否需要 RTOS，故障定位更直接。
- Q2/Q3/Q4 的实机效果有明确来源和回归护栏。
- 迁移期间会暂时保留部分旧函数；只有新所有权路径通过验证后才删除旧入口。
- EdgeTalk 已使用 RT-Thread，其线程拆分和优先级修复属于后续独立变更，不作为 MSPM0
  引入 RTOS 的理由。

## 不采用的方案

- 立即把 `main.c` 中每个大函数机械地变成一个线程。
- 仅靠互斥锁允许多个模块继续写 PWM、方向和 STBY。
- 在一次提交中同时重构调度、迁移 Q3 到 M55并重新调参。
- 用高频 LCD、日志或蜂鸣器刷新证明“系统在运行”。
